# Публикация stdio-моста Projector в npm для npx / bunx

**Date:** 2026-10-09
**Last reviewed:** 2026-10-09
**Priority:** TODO: оператором не задан
**Severity:** TODO: оценка не задана

**Scope affected:** MCP bridge, npm distribution, инструкция подключения
**Probes:** `src/bridge.ts::runBridge`, `src/bridge-entry.ts`, `scripts/build-services.mjs`, `src/main/mcp-setup.ts::getMcpSetup`, `package.json::private`
**Discovered via:** Operator deferral

## Problem And Impact

Сейчас харнесс запускает локальный bridge: в исходниках через системный Node, в packaged `.app` через поставляемый helper. Для подключения без привязки MCP-конфигурации к расположению `.app` оператор хочет публикуемый npm-пакет с командами `npx` и `bunx`.

## Evidence

- `package.json` содержит `private: true`; отдельного публикуемого bridge-пакета и npm `bin` нет.
- `runBridge` связывает стандартный MCP stdio с уже работающим runtime через Unix socket и не запускает приложение.
- Руководство, список инструментов и версия приходят из runtime через `hello`. Пакет-посредник не должен заводить независимую копию инструкций Projector.
- Оператор явно отложил публикацию: «Потом в npm просто опубликуем и будем давать stdio npx/bunx команду».

## Root Cause / Current Hypothesis

Канал npm пока не реализован. Это отдельная поставка существующего транспорта, а не переход на HTTP и не новый runtime приложения. Совместимость Bun ещё не проверена.

## Why Deferred

По решению оператора текущий этап — определение реальных путей для dev и packaged приложения. npm-поставка выполняется следующим отдельным этапом. До неё подключение требует локального пути к bridge/helper.

## Recommended Direction

Создать отдельно публикуемый пакет с `bin` для stdio bridge; сохранить подключение к постоянному Unix socket уже запущенного Projector. Проверить Node и Bun на реальном MCP-цикле; явно указать необходимые версии runtime и команды. Сохранить stdout только для MCP, диагностику выводить в stderr. Проверять совместимость версий bridge/runtime при необходимости; пакет не устанавливает hooks, skills, пользовательские настройки и не запускает приложение автоматически.

Имя/namespace пакета, владелец npm, лицензия, политика закрепления версии в предлагаемой команде и release workflow — TODO: решить перед публикацией. Не рекламировать ещё не опубликованное имя как рабочую команду.

## Resume Conditions And First Actions

1. Возобновить при отдельном запросе оператора на npm-поставку.
2. Выбрать имя и владельца пакета, проверить права на namespace; определить `bin`, поддерживаемые Node/Bun и лицензионные материалы.
3. Собрать tarball и проверить его локально через установку в изолированном окружении без доступа к исходникам.
4. Перед внешней публикацией проверить фактический npm target, полномочия и авторизацию оператора на публикацию выбранного пакета и версии.

## Completion Criteria

- [ ] Пакет устанавливается из tarball; `npx` и `bunx` запускают MCP stdio и подключаются к локальному socket.
- [ ] Подтверждены handshake, инструменты, получение руководства и полный цикл публикации/обратной связи с конкретным Codex.
- [ ] Отсутствующий runtime, разрыв соединения, несовместимость версий и неопределённый результат операции имеют явные диагностики без повторного выполнения мутации.
- [ ] Приложение можно переместить/обновить без изменения npm-команды; выбор нестандартного socket документирован.
- [ ] Нет изменений hooks/skills/AGENTS.md и независимого источника инструкций.
- [ ] Проверены stdout, завершение по EOF и несколько клиентов; штатные npm lifecycle scripts не изменяют окружение пользователя.
- [ ] Пакет опубликован в согласованный registry/namespace с проверенной версией; модалка и README показывают действительно доступные команды и ограничения.
